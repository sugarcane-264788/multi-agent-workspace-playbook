# 一页看懂：协作库的骨架与它为什么长这样

## 0. 它解决什么问题

一个人用 DSH 开多个会话：主对话管日常、邮件会话管邮件、学习线管课程、维护线管资料。
**没有协作库**时，同一件事实会被抄进四份文档，其中三份迟早过期；两个会话同时改一份文件，后写的覆盖前写的；新会话开工要人肉交代半小时。

协作库只做三件事：
1. **划地盘**：每份资料只能被一个会话写（格子）；
2. **通消息**：会话之间不靠用户传话，靠信箱异步收发；
3. **立法律**：每次改动都留痕、可验收、可回滚，事实过期会被自检抓出来。

```
                       ┌──────────────── 用户（人）────────────────┐
                       │ 改主意、给新任务、裁断"这算不算事"      │
                       └───────────────┬─────────────────────────┘
                                       │ 派活 / 汇报
        ┌──────────────────────────────┼──────────────────────────────┐
        │                              │                              │

   │ 主对话   │                │ 维护线        │              │ 业务线们      │
```

## 1. 五个部件

### 1.1 格子（写权边界）

- 一个目录一个主人；**主人之外只读**。
- 共用格（规范、模板、工具、索引）由**维护线**单点写。别的线要改共用格 → 发信要求，不自行动手。
- 判据不是"权限够不够"，是"**这块事实归谁**"。权限全都给成完全权限也没关系，靠职责分工；权限只用来保证"该能写的人真的能写"。

### 1.2 信箱（异步消息）

```
_消息/
  <箱>/                 # 未读
  已处理/<箱>/          # 已归档
  .cursors/<箱>         # 每箱一个游标（上次读到哪封）
```

- **一条线一个箱**，绝不共用（共用必丢信：谁先读谁推进游标，另一条线永远看不到）。
- 信封名机器可读：`<YYYYmmdd-HHMMSS>-from-<发件人>.md`；兜底投递 `from-fallback-*`。
- 正文固定四行头（发件人/收件人/时间 + 第一行"给：<会话名>"），正文开头可带 `error_code: EPERM_WRITE` 这类机器码。
- 读信即归档并推进游标：**读自己的箱是收信，不是偷看**；探别人的箱只加 `--peek`，不动游标。

### 1.3 名册（谁是谁）

- `AUTO` 段：脚本从运行时扫出来（会话 id、状态、有无目录），不许手改。
- 手工段：人写角色、格子、权限、起用时间。脚本只校验"手工段引用的 id 在 AUTO 段里存在"。
- 名册是"我是谁"的唯一权威；会话不确定自己是谁时，跑 `read_state.py --me <id 或角色名>`。

### 1.4 台账 + 索引（改动留痕与检索）

- 台账 `ledger.tsv`：`时间 / 动作 / 路径 / 大小 / sha256 / 说明`。每改一个文件记一行。
- 索引 `_索引.md`：由脚本从全库 `# 标题` + 首段生成，**不许手改**，改了就跑 `kb_index.py`。
- 计划卡（每批活一张）：写清范围、动作、**要改的文件清单**、验收命令、回滚步骤。验收脚本按清单核 sha256，所以"文件改了没记账""记账了文件又被改"都会当场红。

### 1.5 机器层快照（给脚本看的当前状态）

- `_machine/sessions.json`、`_machine/mailbox.json`：纯 ASCII、带 `schema` 版本号、由脚本生成。
- 先定 `schema.json` 再生成；生成物不许手改。
- `read_state.py --doctor` 把快照和盘上对账（会话数、箱未读、游标），不一致就报 `[DRIFT]` 并退出 1。
- 关键设计：**任何全权会话跑一条信箱命令，顺手就把快照刷新**——因为动游标最多的其实是受限档位的会话，它们写不了快照。

## 2. 一天的工作循环

```
开工：digest --for <自己的箱>        # 有没有别人留话
      read_state --sessions          # 认自己（或 --me）
      kb_check.py                    # 全库体检（13 项）
干活：写计划卡 → 改文件
收尾：ledger add（每个文件一行）
      verify --card <卡>             # 台账 sha 一致 + 卡里命令全过
      kb_index.py                    # 索引跟上
      publish --scope all --from <自己的箱>   # 跨格事实变更广播
      status --json                  # 快照跟上（现在多数命令自动做）
      kb_check.py                    # 13/13
      read_state --doctor            # 快照对账
```

顺序不是仪式：`verify` 要在记账后（它核账）；`index` 要在改完之后；`publish` 必须在 `check` 前（第 8 项查"共用格改过就得播报"）；`status --json` 在 `publish` 后（快照得包含新播报）；`doctor` 最后兜。

## 3. 四个层次的自检

| 层 | 查什么 | 成本 | 谁跑 |
|---|---|---|---|
| 1 结构 | 目录骨架、编号唯一、死链、README 在不在 | 秒级 | 每次都跑 |
| 2 一致性 | 修订记录能解析、共用格改过有没有播报、名册与盘上一致、索引不落后 | 秒级 | 每次都跑 |
| 3 语义 | 机器层快照与盘上、schema 合规、纯 ASCII | 秒级 | 收尾必跑 |
| 4 接手演练 | **真开一个新会话**，只给它接手语，看它能不能跑起来 | 分钟级 | 改完接手文档后 |

第 4 层是这套东西最值钱的一层：文档写得再顺，也要新会话跑一遍才知道断在哪。我们改了两轮，新会话报"卡住=无"才算过。

## 4. 五条设计原则（踩过才写得出）

1. **事实只有一个落点**：索引、名册、快照都是生成物；被生成的不要手改，手改的不要被生成。
2. **写库单点**：多会话并行读，写库/记账/播报/重建索引由一条线做。分工靠职责，不靠权限。
3. **规矩落成检查**：能写成 `kb_check` 一项的，就不只写在规范里。写在规范里但没人检查的规矩，三个月后一定形同虚设。
4. **先卡后动 + 台账**：改之前写清"要改哪些文件"，改完让机器核 sha。人写的计划会漏，sha 不会。
5. **人读与机读分开**：人读 markdown（中文、讲道理、带上下文），机读 JSON（ASCII、schema、可校验）。不要逼一份文件同时干两件事。

## 5. 反面模式（我们都踩过）

| 反面模式 | 后果 | 正解 |
|---|---|---|
| 全库转成 JSON 让 AI 直接读 | 中文全没了、长文本转义地狱、人能读的没了 | 人读 md、机读薄快照，中间用 `read_state.py` 转 |
| 两个会话共用一个信箱 | 谁先读谁推进游标，另一个永久丢信且无报错 | 一条线一个箱 |
| 索引手工维护 | 两边漂，检索到旧标题 | 生成器唯一 |
| 把"归档会话"当"停用" | 误报桥挂了，白改一版判据 | 归档=侧栏隐藏，看实际通道证据 |
| 快照只在手动命令里更新 | 别的会话一跑对账就红 | 日常命令顺手同步 |
| 接手文档写给自己看 | 新会话卡在第二条 | 真开新会话跑一遍 |
| 卡外改动"顺手做了" | 台账漏、播报漏、别人不知道 | 先问、补卡、披露偏差 |
