# evals：这个 skill 该不该被触发

每个 skill 一个 `<skill>.json`：

```json
{
  "skill": "session-handoff",
  "version": "2026-10-23",
  "should_trigger": ["...3 条该触发的中文场景..."],
  "should_not": ["...2 条看着像、其实不该触发的..."]
}
```

## 为什么要有这个

skill 的 `description` 决定了它会不会被加载。描述写长了费 token、写短了怕漏触发，光凭感觉判断不了——所以每个 skill 固定配 3 条"该"、2 条"不该"的邻居场景，改描述之后拿这 5 条重判一次。

## 怎么判（两种都行）

1. **自己判**：把 `description` + 那 5 条读一遍，问自己"如果我只看描述，会加载它吗"。3 条该触发的全过、2 条不该触发的都没过，才算描述合格。
2. **派只读子代理判**（推荐，省上下文）：把 `description` 与 5 条场景给它，要求它每条给「加载 / 不加载 + 一句理由」，返回一张表；不要让它改文件。派法见 `delegate-and-reclaim` skill。

## 判定标准（减少主观）

- 该触发的场景里必须含**用户会说的原话**（不是"使用者可能想了解……"这种自述）。
- 不该触发的场景必须是**邻近**的（相邻任务），太离谱的（"今天天气"）没有区分力。
- 判"加载"只看描述，不看 skill 正文——正文加载了才会被读到，判断顺序不能反。

## 改了一个 skill 之后

1. 改 `SKILL.md` 的 `description`；
2. 跑 `python sync_skills.py`（或 `--check`）同步到 `<agent-skills-dir>\`；
3. 用本目录的 5 条重判一遍；
4. 有 skill 触发判定变化时，在 `修订记录` 同一张卡里记一句。

## 已知局限

- 没有自动评分器（判定本身要 LLM），所以这里只放用例与判据，不假装能跑 `pytest`。
- 判据是"该/不该"，不测"触发后答得好不好"——那要靠真实演练（见 `layered-self-check` 的第四层）。
