# 先卡后动 + 台账 + 验收

版本：2026-10-23（v2：收尾七连唯一定义处、补例子）

## 什么时候用

- 要改一份多人/多会话共用的仓库（文档或代码）。
- 用户说：留痕、可回滚、验收一下、别改乱了、改完给我看证据。
- 你自己要改超过 1 个文件，或改的是"别人也在用的"东西。

## 什么时候别用

- 一次性的临时脚本、草稿：不记账，直接扔。
- 纯只读分析：不需要卡，只需要说清结论与出处。
- 单个文件的错别字修正且仓库只有你一个人：说明白了就行。

## 流程

1. **写卡**（改之前）：`40-协作\_计划卡\<日期>-<主题>.md`
2. **改**：只改卡里写了的东西；卡外改动先问，真做了就写进卡里「偏差记录」。
3. **记账**：每个文件一行 `ledger add`（每次改完重记，不是只记一次）。
4. **验收**：`verify --card "40-协作\_计划卡\<卡名>.md"` → 台账 sha 一致 + 卡里命令全过。
5. **收尾**：见下「收尾七连」。

## 卡的结构（两段机器读）

```markdown
# M[N] 标题
> 用户 [日期]：「[原话]」

## 目标          # 做完什么状态叫完成
## 范围（N 个动作）
## 本卡不做       # 防"顺手"
## 文件           # ★ 机器读：每行 `- 文件：<相对库根路径>`
## 动作           # 逐条：改哪个文件、改成什么
## 验收           # ★ 机器读：```verify 代码块（工作目录＝库根）
## 偏差记录（如实记，不藏）
## 回滚           # 备份路径 → 恢复 → 重建索引 → 自检
```

## 收尾七连（全库唯一定义处，其它 skill 引用这里）

```
ledger add → verify --card → kb_index → publish → status --json → kb_check → --doctor
```

顺序的理由：
- `verify` 在记账后 → 它核 sha；
- `kb_index` 在改完后 → 索引要新；
- `publish` 在 `kb_check` 前 → 自检查"共用格改过必须播报"；
- `status --json` 在 `publish` 后 → 快照得包含新播报；
- `--doctor` 最后兜 → 快照与盘上对账。

## 例子（真例，脱敏）

台账（`ledger.tsv`）：

```
ts	action	path	size	sha256	note
2026-10-23T20:28:54	create	40-协作\_计划卡\2026-10-23-M16-…md	2706	<sha>	M16 卡
2026-10-23T20:28:54	edit	修订记录.md	60572	<sha>	第七十九轮
```

verify 输出：

```
[PASS] 40-协作\_计划卡\2026-10-23-M16-….md  create  2706B
[PASS] 修订记录.md  edit  60572B
结果：全 PASS
```

## 验收

- `verify --card` 输出「结果：全 PASS」。
- 反向验证一次：改一个文件**不记账** → verify 报"台账里没有记录"；记账后再改一字节 → 报 sha 不一致。
- 卡里文件清单漏文件 → 改了没人知道（所以清单必须穷举）。

## 常见坑

- 记账后又改文件 → sha 不一致，必须重记。
- 用绝对路径记账 → 换机器/换目录失效。
- `verify` 只给卡名 → 报"找不到计划卡"（要相对库根路径）。
- 卡里写了未来要建的文件 → 死链检查报红（建了再引，或去掉 `.md`）。
- 卡外"顺手改" → 播报漏、别的线按旧理解干活。
