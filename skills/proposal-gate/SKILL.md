# 提案门槛 + 否决账

版本：2026-10-23（v2：与子代理规则拆分）

## 什么时候用

- 用户/自己想说"要不要加个新规矩、新工具、新流程"。
- 你想提出一个机制性改动（不是修 bug、不是补文档）。
- 有人重复提一个"感觉之前拒过"的想法。

## 什么时候别用

- 只是在修一个明确的 bug、补一句文档：不需要提案门槛。
- 用户已经批准、只要执行：别拿门槛拖时间。
- 内容只是"某个数字改成另一个"：按普通改动走卡即可。

## 门槛：一句话

> 提新机制先说：**现在哪里会疼**——哪次会话、哪一步、什么症状；有输出就贴输出。
> 写不出具体现象 = 没疼到该动。

不需要长模板。一句现象 + 一句"现在怎么绕过去"就够。原因：
- 规则越多执行越差；活下来的规矩都是被事故咬过。
- 否决过的不落账，就会被反复提（本库真实经历：两小时内提了两次"全表转 JSON"）。

反例（别这么写门槛）：要求"每次小改都写一段 observed failure" → 拖成每件事先生文档，最后没人写。

## 否决账（`_否决/`）

一条一个文件，四段固定：

```markdown
# <提案名>
- **现象**：哪次、哪步、什么症状
- **为什么否**：根因；否的是做法还是需求
- **现在走什么**：替代方案，具体到命令/文件
- **再提条件**：什么事实变了可以再提；没有就写"暂不重提"

## YYYY-MM-DD 复核：条件已满足 → 解禁   # 只追加，不改旧结论
```

规则：
- 再提之前先查：`grep -ril "<关键词>" <库>\40-协作\_否决\`。
- 目录要进自检骨架（`_否决/README.md` 存在）、进目录结构文档，否则会被当临时目录删掉。
- 解禁只追加一节，不改原文（历史结论要留证据）。

## 例子（真条目骨架）

```
# 规则全表转 JSON
- 现象：用户要求"AI 读得更省"后，想把八张规范整体转 JSON；转换脚本刚写就出现中文丢失、长文本转义。
- 为什么否：长文档是给人读的；AI 费力的是长度不是格式。转完两份真相，没人维护。
- 现在走什么：只转薄状态（sessions/mailbox），人读部分保持 markdown，中间用 read_state.py。
- 再提条件：出现"必须机器可校验的字段"超过 3 处、且 markdown 已不能表达。
```

## 验收

- 新提案能用**一句话**说出疼点（含具体会话/步骤/症状）。
- 提之前 grep 过 `_否决\`，没有同题；提之后若被否，24 小时内落成一条账。
- 自检里确有 `_否决/README.md` 的骨架检查。

## 常见坑

- 否决账只写"不建议"没写替代方案 → 下次还是同一个问题重开。
- 改旧结论而不是追加复核 → 证据链断了。
- 门槛写成流程审批 → 小改动也卡，最后所有人绕过去。
